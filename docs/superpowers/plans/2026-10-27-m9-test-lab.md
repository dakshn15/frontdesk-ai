# Milestone 9: test lab and evaluation suite

**Goal:** Owners check the receptionist before and after going live, in three ways:

- a playground that shows how each answer was made, with a "Fix this answer" button;
- saved test questions with simple, explainable checks, run in one click, with the results kept;
- questions from real chats where the receptionist wasn't sure, each one click from becoming a test.

The demo salon's tests also run nightly against the real models in GitHub Actions.

**Spec:** [4.8 Test lab](../specs/2026-10-24-frontdesk-ai-design.md) and the evaluation suite in section 8.

**Architecture:**

- **Test cases** are business data under RLS: members read them, managers write them.
- **Runs and results** are written by the server (`src/privileged/testlab/`). Each test runs the same agent as the live chat, in dry mode, on a conversation in a new `test` channel, so analytics can leave them out.
- **Checks** are a pure function: tools used, text it must or mustn't contain, "must say it isn't sure", "must hand off".
- **The optional AI grader** compares meaning with an expected answer. It's skipped, not failed, when no AI key is set.
- **Execution:** a run executes after the response (`after()`), and its page refreshes while it's running.

## Global constraints

- Copy is plain, with no exclamation marks.
- Migrations go to production before the code.
- TDD for the logic, one e2e run at the end.
- No new dependencies.
- Tests run as dry runs: no bookings, leads or emails.

## Tasks

1. **Tests, runs and checks.**
   - Migration:
     - `test_cases`, `test_runs` and `test_results`;
     - the `test` conversation channel;
     - grants.
   - `src/features/testlab/`:
     - `schemas.ts`, the test form: at least one check, up to 50 tests per workspace;
     - `checks.ts`: `evaluateChecks`;
     - records for adding, editing and deleting tests, under RLS;
     - queries for tests, runs, results, and questions to review (low or no knowledge confidence in website chats from the last 30 days, not yet tests).
   - `src/privileged/testlab/`:
     - `startTestRun`: one run at a time per workspace, and 5 runs an hour;
     - `executeTestRun(runId, { model, grader })`;
     - `gradeAnswer`.
   - The demo seed adds 8 of the salon's tests, 5 of them marked "must pass".
   - Tests:
     - unit tests for checks, the schema and parsing the grader's verdict;
     - integration tests for RLS, the run limits, and a full run with the scripted model on a demo sandbox (expected passes and failures with their explanations), plus the grader with a mock model.
2. **Test lab pages.**
   - The nav's Assistant item becomes "Test lab", with tabs for Playground and Tests.
   - **Playground:** the M5 preview chat, plus an inspector for the selected reply:
     - the tools with their input and output;
     - the passages found;
     - the verified answer used;
     - the model, tokens and response time, sent in the stream's metadata for the dashboard preview only;
     - "Fix this answer" saves a verified answer.
   - **Tests:**
     - the list with add, edit and delete;
     - "Run all tests";
     - run history with pass counts;
     - questions to review, with "Add as test".
   - **Run page:** each result with the answer, tools used, and why it failed.
   - E2E: add a test, run all tests and see pass or fail with a reason; in the playground, see the inspector and fix an answer.
3. **The nightly evaluation.**
   - The `eval` vitest project (`tests/eval/`): seeds a demo sandbox, runs its tests with the real model and grader, writes a summary to the GitHub job summary, and fails if a must-pass test fails. It's skipped without a key.
   - `.github/workflows/eval.yml`: runs nightly and on demand.
   - A README badge.

## Review focus

- A run that never finishes (a crash mid-run): a run stuck "running" for over 15 minutes no longer blocks new runs, and shows as failed.
- Tests creating real bookings or emails: dry mode, covered by the scripted run.
- Staff or other workspaces editing tests: refused by RLS.
- The AI grader without a key: skipped with a note, and doesn't count as a failure.
- Demo visitors running tests: dry runs count against the shared daily demo AI cap.
