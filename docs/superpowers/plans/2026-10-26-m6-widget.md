# Milestone 6: chat widget

**Goal:** A business pastes one script tag on its site and visitors get the receptionist in a floating chat: streaming answers with source chips, booking cards they confirm with their name and email, a lead form, a handoff state, and a transcript that survives reloads. The widget only loads on the business's own domains.

**Spec:** [4.6 Chat widget](../specs/2026-10-24-frontdesk-ai-design.md), plus the widget parts of sections 5 and 7.

**Architecture:** `/embed.js` is a tiny plain script. It adds one fixed-position iframe pointing at `/widget/[slug]`, and resizes it when the iframe posts `frontdesk:state` messages, checking that they come from the app's origin. Everything visible, including the launcher button, lives inside the iframe, so the host site's CSS can't touch it. The iframe page talks to the M5 chat API, plus three new widget endpoints: history, book and lead. They all live in `src/privileged/widget/`.

## Global constraints

- Copy is plain, with no exclamation marks.
- Migrations go to production before the code.
- TDD for the logic, one e2e run at the end.
- Lockfile rules as in memory.
- No new dependencies.

## Tasks

1. **Settings and domain rules.**
   - Workspace columns: `widget_color` (hex), `widget_greeting`, `widget_suggestions text[]` (up to 4), `widget_position` (`right`/`left`) and `allowed_domains text[]` (up to 10).
   - `booking_source` gains `widget`.
   - Column grants for managers.
   - `src/features/widget/domains.ts`: `normalizeDomain`, `hostAllowed(host, domains)` (an exact match or any subdomain; an empty list allows any site) and `frameAncestors(domains)`, which builds the CSP value.
   - A Widget page in the dashboard (`/w/[slug]/widget`): the settings form, the embed snippet with a copy button, and a "Try it" link.
   - Tests: unit tests for domains and the schema; integration tests for saving through RLS (staff can't save).
2. **Widget API.**
   - `src/privileged/widget/`:
     - `config` (public settings for a slug);
     - `history` (messages for the session's conversation, with its status);
     - `confirmBooking`, which books only a time this conversation's `propose_booking` offered, then sends the confirmation email and saves a short AI message;
     - `saveLead`.
   - Every endpoint also checks two things:
     - the `Origin` header, which must be absent or the app's own;
     - the session's host, captured at session start from the iframe's parent and checked against the allowed domains (403 otherwise).
   - Rate limits: 5 bookings and 5 leads per session per hour.
   - Routes: `/api/widget/history`, `/api/widget/book` and `/api/widget/lead`.
   - Tests: integration tests for each rule.
3. **Embed script and widget UI.**
   - `src/app/embed.js/route.ts`: the script, cached for 5 minutes.
   - `src/app/widget/[slug]/page.tsx` with `widget-chat.tsx`:
     - launcher, panel, greeting, suggested questions, streaming replies, source chips;
     - booking card with a confirm form;
     - handoff banner, lead form;
     - the session and conversation kept in `sessionStorage`;
     - full screen below 480px.
   - The proxy skips Supabase session work for `/widget`, `/embed.js` and `/api/widget`, and sets `Content-Security-Policy: frame-ancestors` on `/widget/*` from the allowed domains.
   - The dashboard preview shows booking cards read-only.
   - The fake model proposes the first free slot when the visitor says "book".
   - E2E: the embed script on a blank page opens the widget and answers; booking through the widget card shows up in the dashboard calendar.

## Review focus

- A host site embedding the widget for another workspace's slug: frame-ancestors blocks it once domains are set.
- Booking a time the AI never offered, or one taken since it was offered: refused.
- Posting messages to the embed script from another origin: ignored.
- A reload mid-conversation: the transcript comes back, and so does the handoff state.
- A phone-width screen: the panel fills the screen and the close button stays reachable.
